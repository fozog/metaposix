# metaposix

A prototype portability layer for POSIX.1-2024 facilities, with runtime shims
and a separate validation executable. This is not a complete POSIX
implementation or a conformance certification.

## Project layout

- `include/`: interposed POSIX headers and compiler/platform definitions.
- `src/`: runtime shim implementations, built as `libmetaposix.a`.
- `tests/`: validation runner and integer/string, threading, filesystem,
  networking, and asynchronous I/O tests, built as `mp_tests`.
- `CMakeLists.txt`: CMake configuration for the library and validation program.
- `Makefile`: independent plain-Make fallback, not generated by CMake.

Generated files belong in `build/`, not beside source files. CMake rejects
in-source builds.

## Using the portability layer

Add the library's `include/` directory before system include paths, link
`libmetaposix.a` and its platform dependencies, and make this the first include
in each C source file:

```c
#include "metaposix.h"

#include <stdlib.h>
#include <pthread.h>
```

Keep the normal headers for the APIs you use. `metaposix.h` centralizes
`_POSIX_C_SOURCE`, Darwin extensions, and Linux GNU extensions; applications
should not duplicate those definitions or need OS-specific preambles.
It must appear before any system header, including headers included
indirectly or through precompiled headers. An explicitly configured
`_POSIX_C_SOURCE` older than 200809L is rejected.
This feature-test baseline does not claim complete POSIX.1-2024 support.

## Prerequisites

- CMake 3.16 or newer.
- A GNU-compatible C compiler, such as GCC, Clang/Apple Clang, or Arm Compiler 6
  (armclang), with a suitable target C library and POSIX environment.
- Make for the examples below, which use CMake's `Unix Makefiles` generator.
- POSIX threads, filesystem, and socket support for the validation program.

On macOS, install the Xcode command-line tools (`xcode-select --install`) and
CMake. Native MSVC is not supported: the current implementation depends on
POSIX APIs and GNU-style `#include_next`.

The shim library uses C11. Validation enables C23 mode (`-std=c2x`) when the
compiler probe detects 128-bit `_BitInt` support; otherwise that test reports
`SKIP`. This does not imply full C23 support from the compiler or C library.

## Configure, compile, and execute locally

Run these commands from the project root:

```sh
cmake -S . -B build/native -G "Unix Makefiles" \
  -DCMAKE_BUILD_TYPE=Debug
cmake --build build/native --parallel
ctest --test-dir build/native --output-on-failure
```

Configuration selects and checks the compiler and generates Makefiles.
The build produces `build/native/libmetaposix.a` and `build/native/mp_tests`.
CTest executes the validation program and reports its exit status.

To run it directly and see all `PASS` and `SKIP` messages:

```sh
./build/native/mp_tests
```

For optimized code, use a separate directory with
`-DCMAKE_BUILD_TYPE=Release`. To inspect compiler commands:

```sh
cmake --build build/native --verbose
```

The sample uses temporary files under `/tmp`, loopback TCP connections, and
local socket pairs. Run it in an environment permitting those operations.
Unicode conversion tests depend on the active locale and can report `SKIP`
when a suitable locale is unavailable.

### Select GCC or Clang

Select the compiler on the first configuration of a fresh build directory:

```sh
cmake -S . -B build/gcc -G "Unix Makefiles" \
  -DCMAKE_C_COMPILER=gcc -DCMAKE_BUILD_TYPE=Debug
cmake --build build/gcc --parallel
ctest --test-dir build/gcc --output-on-failure

cmake -S . -B build/clang -G "Unix Makefiles" \
  -DCMAKE_C_COMPILER=clang -DCMAKE_BUILD_TYPE=Debug
cmake --build build/clang --parallel
ctest --test-dir build/clang --output-on-failure
```

You can supply an absolute compiler path instead of a command name.
On macOS, `gcc` commonly names Apple Clang; use the actual GCC executable
(which may have a versioned name) to select GNU GCC.

Do not switch compilers, SDKs, targets, or generators in an existing CMake
build directory. Use a new directory for each configuration. CMake-generated
Makefiles already record the compiler: select it during CMake configuration,
not with `make CC=...` afterward.

### Select a macOS architecture

Apple Clang and the macOS SDK can target either architecture:

```sh
cmake -S . -B build/macos-arm64 -G "Unix Makefiles" \
  -DCMAKE_C_COMPILER=clang \
  -DCMAKE_OSX_ARCHITECTURES=arm64 \
  -DCMAKE_BUILD_TYPE=Debug
cmake --build build/macos-arm64 --parallel
```

Use `-DCMAKE_OSX_ARCHITECTURES=x86_64` for Intel macOS, or
`'-DCMAKE_OSX_ARCHITECTURES=arm64;x86_64'` for a universal binary.
The SDK and all linked libraries must support the requested architectures.

Execute the ARM64 build on an ARM64 Mac:

```sh
ctest --test-dir build/macos-arm64 --output-on-failure
# Or:
./build/macos-arm64/mp_tests
```

An Intel Mac cannot run an ARM64 executable natively. An ARM64 Mac may run
x86_64 executables if Rosetta is installed. Building successfully does not
establish that every requested architecture has been tested.

## Cross-compile with a toolchain file

A toolchain file specifies the target OS, compiler, architecture, and
SDK/sysroot before CMake performs compiler checks. Setting only
`CMAKE_SYSTEM_PROCESSOR` does not change the instructions generated by a
compiler.

For example, on an x86_64 Linux host with an ARM64 Linux cross-toolchain,
create a file such as `cmake/toolchains/linux-arm64-gcc.cmake` containing:

```cmake
set(CMAKE_SYSTEM_NAME Linux)
set(CMAKE_SYSTEM_PROCESSOR aarch64)
set(CMAKE_C_COMPILER aarch64-linux-gnu-gcc)

set(CMAKE_SYSROOT "/absolute/path/to/target/sysroot")
set(CMAKE_FIND_ROOT_PATH "${CMAKE_SYSROOT}")
set(CMAKE_FIND_ROOT_PATH_MODE_PROGRAM NEVER)
set(CMAKE_FIND_ROOT_PATH_MODE_LIBRARY ONLY)
set(CMAKE_FIND_ROOT_PATH_MODE_INCLUDE ONLY)
set(CMAKE_FIND_ROOT_PATH_MODE_PACKAGE ONLY)
```

This is a template, not a supplied toolchain file: replace the sysroot path
and compiler with your installed SDK's values. The sysroot must contain
matching target headers, libraries, and runtime files. Some SDKs configure
their sysroot automatically; follow their documentation.

Configure and build:

```sh
cmake -S . -B build/linux-arm64 -G "Unix Makefiles" \
  -DCMAKE_TOOLCHAIN_FILE=cmake/toolchains/linux-arm64-gcc.cmake \
  -DCMAKE_BUILD_TYPE=Release
cmake --build build/linux-arm64 --parallel
```

With a Clang-based SDK, the toolchain can instead select `clang` and set
`CMAKE_C_COMPILER_TARGET` to the SDK's target triple, for example
`aarch64-linux-gnu`. You still need the target sysroot, linker, and runtime;
Clang alone does not provide them.

### Execute on the target

Do not run an ARM64 Linux executable directly on an x86_64 host. For a target
reachable over SSH, replace `user@target` below:

```sh
scp build/linux-arm64/mp_tests user@target:/tmp/metaposix-mp_tests
ssh user@target 'chmod +x /tmp/metaposix-mp_tests && /tmp/metaposix-mp_tests'
```

The target must have a compatible OS, dynamic loader, and runtime libraries.
The shim archive is linked into this executable, but that does not make all
system dependencies static.

Alternatively, if QEMU user-mode emulation is installed on the Linux host,
configure a fresh build directory with an emulator:

```sh
cmake -S . -B build/linux-arm64-qemu -G "Unix Makefiles" \
  -DCMAKE_TOOLCHAIN_FILE=cmake/toolchains/linux-arm64-gcc.cmake \
  '-DCMAKE_CROSSCOMPILING_EMULATOR=qemu-aarch64;-L;/absolute/path/to/target/sysroot' \
  -DCMAKE_BUILD_TYPE=Debug
cmake --build build/linux-arm64-qemu --parallel
ctest --test-dir build/linux-arm64-qemu --output-on-failure
```

CMake prefixes the registered test command with the emulator. Emulation is
not equivalent to validation on real hardware.

### Arm embedded toolchains and RTOS targets

`armclang` and `arm-none-eabi-gcc` require target-specific SDK settings:
CPU, ABI, floating-point options, startup code, linker script, and RTOS
headers/libraries. A compiler selection alone does not supply POSIX support.

The current standalone build requires POSIX threads and always defines the
validation executable. Its platform capability map is a prototype, not a
complete RTOS configuration system. It does not yet provide a generic
bare-metal firmware build or a ready-to-use RTOS toolchain file.

For Zephyr, integrate the library with Zephyr's board, SDK, and CMake
configuration rather than replacing that workflow with a generic toolchain.
Other RTOS targets likewise need their own integration and missing-facility
backends before the validation suite can be expected to build or run.

## Build just the library

After configuration:

```sh
cmake --build build/native --target metaposix --parallel
```

This builds the archive without building `mp_tests`, but configuration still
checks the project's current dependencies and defines validation targets.
There is not yet a configuration option to disable validation altogether.

## Plain Make alternative

For native builds without CMake:

```sh
make check
```

Outputs go under `build/make`. To select a compiler and keep its outputs
separate:

```sh
make CC=clang BUILD_DIR=build/make-clang check
make CC=gcc BUILD_DIR=build/make-gcc check
```

The plain Makefile uses the host OS to select some flags. Prefer CMake
toolchain files for cross-compilation.
